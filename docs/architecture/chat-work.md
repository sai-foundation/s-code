# Chat and Work design

Decision record for [issue #72](https://github.com/sl-7qx/s-code/issues/72).

## Decision

A Session has an explicit `chat` or `work` mode. Chat has an empty
`workspace_uri`; Work has a local directory URI. The Web creates Chat by default.
Existing sessions and API requests without a mode retain Work semantics.
Migration 0047 adds the mode with a Work default and an encrypted, optional
`work_reason`. Empty workspace settings support first-run Chat without a project.

The boundary belongs to the host. Chat receives conversation history and
user-uploaded attachments, but skips instruction discovery, skills, project
memory, editor context and MCP resources. Its only model tool is `start_work`. Persistent Goal creation and updates are
restricted to Work in storage and the Web, so Chat cannot enter an automatic
continuation loop without access to Goal completion tools.
The daemon checks the mode before tool preparation and hooks; the execution
service also rejects direct tool submissions for Chat. Workspace search and
background terminals require Work. A model-generated tool name cannot grant
itself additional authority.

## Transition

`start_work({reason})` is a host operation. It takes no path argument. An
explicit user request uses `POST /v1/sessions/{session_id}/work` with scope and
reason. Both preserve the Session ID and history. User-driven promotion waits
until the Session is idle; model-driven promotion requires its owning live turn.

A daemon mutex serializes promotion, while the storage update independently
checks the Session's active state and the turn's status. Repeated user requests
return the existing Work Session. Directories receive host-generated identifiers,
are private, and live separately from protected application state. Symbolic-link
roots are rejected. If admission fails after folder creation, cleanup uses only
`remove_dir` on that empty folder; it never recursively removes content. A process
crash before database commit can leave an empty orphan folder, which is safe to
remove manually. This feature does not delete workspace data on session deletion.

For model transitions, all fallible Work context and catalog preparation happens
before the mode changes. A failed preparation removes its empty directory and
leaves the Session in Chat. Skill selection uses the current user prompt, just
as in an ordinary Work turn.

Storage commits the workspace, mode and encrypted reason together. The daemon
publishes `session.mode_changed`; clients also read the authoritative Session
from snapshots after reconnect. A lost event does not lose the mode or reason. After commit, publication failure
is logged and the committed transition still returns to the model.
Tool completion is published in order after the proposed event so the Web does
not leave the transition card pending.

The host returns a typed `ContextChanged` result to the agent runner. It replaces
the tool catalog and the exact Chat-mode instruction for the next model request,
while preserving conversation messages, compaction summaries, persistent goal
context and tool results. This metadata is generated by trusted
host code, never decoded from arbitrary tool output. The Work context uses the
normal editing profile and permission mode. Approvals and sandbox restrictions
remain in force. Existing Work or review tasks cannot use `start_work` to change
their tool profile.

## Alternatives and limits

Creating a hidden directory for every Chat would grant unnecessary workspace
authority and create unused folders. Keyword-based routing would confuse a
question about code with a request to modify files. Instead, the model makes an
explicit tool call whose effects are visible and checked by the host.

This version supports one-way promotion. It does not move an existing project's
files, attach arbitrary existing paths through model arguments, or automatically
switch Work back to Chat. A user can start another Chat. The same-OS-account
attacker boundary remains the existing security model; private folders and path
validation do not isolate the application from an attacker controlling its user.

## Verification

Regression tests cover Chat Q&A without a directory or local tools, the complete
Chat-to-Work-to-file-edit loop without Git, direct and forged tool rejection,
foreign scope, concurrent/repeated promotion, cancellation, Chat forks, legacy
API defaults, empty settings, and symbolic-link roots. Web tests cover explicit
mode selection, ignoring old default directories, legacy sessions and validated
in-place transitions. Independent browser checks exercise both explicit and
model-triggered promotion, approvals, retained messages and reload recovery.
